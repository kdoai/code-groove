# R13 — 監査から採用した改善

目的に直結する比較の根拠・判断の区分・探索経路を改善する。網羅的な自動レビューへ機能を広げることより、確認したパターンと違いを人が検証できることを優先した。

| 採用した点 | 処理と保証 | 限界 |
|---|---|---|
| 全域の探索 | `list_units(scope=repository)`に名前・パスの絞込みとページ分割。`inspect_relations`も範囲外の関数から次の関係を追える | 静的索引にない動的関係は解決しない。分類・完了表示は現在の範囲のみ |
| 設計パターンと比較 | 非重複の2実装以上の完全な読取、観察内容、範囲、理由のある例外。比較先のunit・正確なspan・証拠を検証 | 妥当な意味解釈かどうかは構造検証だけでは証明できない。多数派の良否判定ではない |
| 三つの判断区分 | `review_axis`: correctness / quality / coherence。一般的な品質の懸念は作風の一致と分離 | 独立した網羅的なSecurity等の検査工程ではない。実行テストも行わない |
| 人への確認事項 | `inconclusive`と`human_review_required`、具体的な確認事項。判断保留を懸念の音にしない | 設計責任者からの回答・解決履歴は別途必要 |
| 比較と音の追跡 | v9のパターン種別ごとの固定伴奏。根拠付きCoherence比較では2打目を160 ticks遅らせる。cueは指摘ID・元イベント・比較証拠を保持 | 比較先が別範囲ならコード比較は可能だが、その範囲の全体演奏は生成しない。聴取効果は未実証 |
| UIの正確さ | 対象と比較先のコードを並べ、正確な関数範囲へ移動。公開記録は保存された説明を見る操作と新規調査を分離 | 既存Tsugiai記録にはR13のパターン判断を創作しない |
| 保存と大きい入力 | 同じsnapshotの旧Agent結果は読めるが現行キャッシュとは区別。再検査は明示操作。小さい差分のために大きい入力全体を512 KBで拒否する不整合を修正 | 4 MiB / 200 KiB毎ファイルと64,000文字の差分上限は維持 |

追加モデル工程、追加サービス、ベクトルDB、常時バックグラウンド解析、Security等20観点の全件検査、多数派からの自動問題認定は採用していない。既存Google Gen AI SDKのloop・18/8モデルrequest・48/20ツール・トークン予約・480/180秒・1ユーザー10回/UTC日・全体予算・7日保存を保持する。費用は既存run内の必要な読取に限定し、追加段階のモデルrequestは設けない。実際のtoken増減はR13実モデル検証を行っていないため未計測。GCPはTokyo、min0、webmax2 / workermax1 / Tasks同時実行1を維持する。

パターンの抽出は既存の解析と追加調査の提出に含まれる。追加調査の新規・改訂パターンは、各事例を今回読み直した証拠が必要。人が解釈を反映するときに保存し、元のコードや以前の解釈を上書きしない。Correctness / Quality・判断保留・理由のある違いは懸念cueを生成しない。新しい比較を持たない古いoverview録音もcueを追加しない。12保存譜面は新しいgrammar/hashへ0モデルで更新し、全notesと元map/source/traceを保持した。

パターン種別から選ぶ伴奏テンプレートは、domain_rule / responsibility / layer_boundary / dependency_direction / error_strategy / namingの順に既存の6固定リズムを使う。意味イベントの主要打点・旋律・強さは変更せず、重ねる伴奏の反復規則を変える。懸念数を音量や深刻度へ変換しない。grammarと固定SemanticMapが同じなら譜面は再現するが、新しいAI解析が毎回同じパターン解釈を返すことは保証しない。

残る重要な課題は、範囲間の責務・概念・パターンの統合、Pythonの入れ子関数等の索引粒度、独立したリスク検査の範囲選択、意味判定の実モデル評価、発音イベント0件の解釈保存と音楽失敗の分離。今回の局所比較をRepository全体の設計文法の完全な獲得とは呼ばない。
