保存済みの実解析6件を元のソース・契約文書と照合しました。処理説明は概ね対応していますが、確認候補には反例のある一般化が1件あり、設計意図や根拠範囲にも不足がありました。確認候補の表示は、人が根拠と反証を読む入口として扱う必要があります。

これは過去の選択された出力に対する**ソース支持の評価**です。現在のAgent全体の正解率、欠陥検出の適合率・再現率、音の分かりやすさは測定していません。

## 理由のある例外・網羅性・音との関係

| ソースから確認した事項 | 保存済み解釈の扱い |
|---|---|
| justifiedの一般30日/非最終セールと法人90日/レシートは別契約 | 別責務とし、無条件の統合仮説を棄却。追加調査も契約差を理由として保持している |
| justifiedのテスト名のファイルは契約コメントと例配列のみ | 契約文書の補助にはなるが、assertionのある実行テストやテスト合格の証拠にはならない |
| scatteredの同じ返金条件、returns-beforeの同じ期限・明細・手数料 | 同じ責務・対応するconcept_keyを使用。配置の比較に必要な関係を保つ |
| returns-afterのチャネル別保存・監査 | 共通ポリシーを分離した後も、共通の保存/監査concept_keyと責務を保持 |
| checkoutのキャンペーン条件・割引式はpricing/rewards/previewにある | 分散候補はpricing/rewardsの二箇所を挙げ、previewを含む共通政策の範囲を説明しきれていない |
| checkoutの同じ条件が3つの責務・別concept_keyへ割り当てられている | 価格・特典・プレビューという上位の分担自体は妥当。ただし共有する下位政策を音から認識できるかは課題。3つの役割を無条件に同一視せず、下位の共通関係を確認する必要がある |
| Tsugiaiのparking追加/完了更新には対象不在でもsuccessを返す分岐がある | 主な更新処理は説明されるが、不在時の戻り値条件は未収録。「更新が必ず成功」は支持できない |
| Tsugiaiの不一致文面はexpected_answerとng_item_ids所属から作られる | 抽出処理の配置は説明される。呼出元のng_item_idsの意味と契約が揃うかは本評価では未確認 |
| Tsugiaiの並行実行、各保存処理の外部サービス成功、未選択範囲 | 実行時の事実は不明。openや未調査を問題なしへ変換しない |

これはソース由来の確認事項との照合です。独立した網羅的正解集合がないため、見落とし率・再現率は算出しません。音の聴きやすさや、同じ政策を認識できるかの効果も未測定です。

## 再集計と次の評価

[個別判定99件と評価基準](../evaluations/recorded-interpretation-v1.json)に、項目ID・判定理由・リンクされたソース範囲・入力ファイルのSHA-256を保存しています。次のコマンドは保存データの読取と判定の再集計だけを行います。解釈を自動採点し直すコマンドではありません。

```powershell
uv run python scripts/evaluate-recorded-interpretation.py
```

入力の変更、判定の欠落・重複、不正な根拠範囲・参照・ハッシュを拒否します。ローカル集計を保存する場合は `--report .local/interpretation-assessment-summary.json` を付けます。

一般的な解釈精度を測るには、現行プロンプトを固定し、開発時に未使用の例で、根拠を読んだ複数の人が先に正解・別解・保留を定義する必要があります。欠陥候補だけでなく、理由のある例外、判断保留、未調査を含め、責務一致、説明支持、過剰断定、反証の扱い、重要条件の見落としを別々に評価します。複数回の解析による揺れと、人の判断の一致も測ります。

新規解析が必要な評価は、利用者が明示的に依頼した操作として行います。本評価は現行 `conductor-system-v14-counter-integration` の新規実行を含まず、その精度を示していません。
